## Findings fixed with RED then GREEN

Every finding below was discovered by actually building and running the Docker artifacts end to end (`docker build`, `docker compose up`, real migrations, real HTTP calls, real container logs), not by reading the config files. Five were found during this task's own build-and-run cycle; five more were found by an independent `code-reviewer` countercheck dispatched over the diff before sealing (see "Independent review").

### 1. `ENV NODE_ENV=production` in the Dockerfile's shared `base` stage broke `npm ci` in the `build` stage

`base` set `NODE_ENV=production`, inherited by `build`. npm's legacy behavior silently omits devDependencies whenever `NODE_ENV=production` is set in the environment, even for a full `npm ci` with no `--omit=dev` flag, so `nest build` failed with `sh: 1: nest: not found`. Confirmed pre-existing by building `git show HEAD:BE/Dockerfile` unmodified: same failure.

Fix: moved `ENV NODE_ENV=production` to the `runtime` stage only. `deps` and `build` now install with a clean environment.

GREEN: `docker build -t quan-ly-sach-be:local -f Dockerfile .` completes; `build:api`/`build:worker` both produce `dist/`.

### 2. `migrations/` was never copied into the Docker image

`dist/tools/db-cli.js up` inside the built image failed with `ENOENT: no such file or directory, scandir '/app/migrations'`: no `COPY` instruction in any stage referenced the `migrations/` directory.

Fix: added `COPY --chown=node:node migrations ./migrations` to the `runtime` stage. (`migrations/` is a `backbone.yml` protected path; this only references the existing directory from a `COPY` in `BE/Dockerfile`, a file outside that path, and does not modify anything under `migrations/` itself.)

GREEN: `node dist/tools/db-cli.js up` inside the container applies all 10 migrations (see "Local proof").

### 3. `CatalogModule` imported `CirculationModule` without `forwardRef`, crashing only the worker entrypoint

`CirculationModule` already imported `CatalogModule` via `forwardRef(() => CatalogModule)`, but `CatalogModule`'s import of `CirculationModule` was a bare, non-`forwardRef` import. The asymmetry caused `UndefinedModuleException` specifically when Nest resolved the module graph starting from `WorkerModule` (not `AppModule`), because CommonJS circular-require resolution order differs between the two entrypoints. `dist/worker.js` had never actually been run before this task.

Fix: wrapped the import in `BE/src/modules/catalog/catalog.module.ts` as `forwardRef(() => CirculationModule)`, matching the existing pattern already used for `DigitalModule` in the same file.

GREEN: `node dist/worker.js` boots and logs `Worker context started`; confirmed no other module reintroduces an asymmetric circular import (`grep -rn "circulation.module\|catalog.module" src/modules`, cross-checked by the independent countercheck).

### 4. `OutboxWorkerRunner`'s main loop had no error handling, matching the exact restart-loop anti-pattern `docs/07-operations.md` section 6 warns against

Any transient failure (`runMaintenance`, `scanDueReminders`, or `processBatch` throwing — e.g. schema not migrated yet, a DB blip) crashed the entire worker process. Combined with `compose.prod.yml`'s `restart: unless-stopped`, this reproduces exactly the pattern the project's own ops doc forbids ("SMTP outage tạo backlog và cảnh báo, không làm API tra cứu restart liên tục"). Discovered via real container log inspection during local smoke testing, not by static review.

RED: `test/unit/outbox-worker.runner.spec.ts` — a scheduler mock that throws on its first call; ran before the fix and confirmed the unhandled rejection propagated out of `runUntilStopped()`.

Fix: wrapped the loop body in try/catch; on error, logs and backs off via the configured poll interval instead of propagating.

GREEN: same test passes; the worker process survives the injected failure and continues on the next tick.

### 5. Three hardcoded, well-known development fallback secrets would silently activate in production if an operator forgot to set the real env var

`AuthConfigService` fell back to `'local-dev-csrf-secret'` and `'local-dev-rate-limit-secret'`; `MessagingConfigService` fell back to a fixed base64 key (`Buffer.from('01234567890123456789012345678901')`) for `OUTBOX_ENCRYPTION_KEY`, the key that encrypts raw password-reset/activation tokens at rest. All three directly violate `BE/docs/07-operations.md`'s "API/worker không được tự chạy với password/key fallback" rule; the outbox encryption key is the most severe of the three.

RED: `test/unit/auth-config.service.spec.ts` and `test/unit/messaging-config.service.spec.ts` constructing each service under `NODE_ENV=production` with the env var unset, expecting a throw; confirmed both booted silently with the fallback before the fix.

Fix: new `BE/src/config/require-production-secret.ts` exporting `requireProductionSecret({ key, isProduction, usedFallback })`, which throws `ConfigurationError` when both are true. Applied at all three call sites.

GREEN: all three now refuse to boot under production without an explicit value; booting succeeds once the real env var is set.

## Findings from the independent countercheck, fixed with RED then GREEN

A `code-reviewer` subagent was dispatched over the full S7-02 diff before sealing (Dockerfile, `compose.prod.yml`, `nginx.conf`, `catalog.module.ts`, `require-production-secret.ts` and both call sites, `outbox-worker.runner.ts`), with instructions to verify empirically, not just read. It ran `npm run build`/`typecheck`/`eslint`/the new specs, plus four live Docker probes, and found 5 confirmed blocking-class bugs beyond the five above.

### 6. Non-root `USER node` could not write to the digital-asset storage volume

Docker creates a missing bind/volume mountpoint as root before the container's entrypoint runs, so the `digital_storage` named volume (mounted at `/app/storage/digital-assets`) stayed root-owned; the first upload as `node` (uid 1000) would fail with `EACCES`. Confirmed live by the countercheck: a fresh named volume mounted into the pinned base image as uid 1000 produced `drwxr-xr-x root root` and a failed `touch`.

Fix: `RUN mkdir -p /app/storage/digital-assets && chown -R node:node /app/storage` added to the `runtime` stage, before `USER node`.

GREEN: rebuilt the image and re-ran the full stack; `docker exec docker-api-1 sh -c "id && touch /app/storage/digital-assets/probe.txt"` returns `uid=1000(node)` and `WRITE_OK` (see "Local proof").

### 7. No mechanism provisioned the dedicated `app`/`migration` MySQL users the design already called for

`env.production.example` already documented "runtime app/worker user: DML only, not the migration account," but nothing created those users: a fresh `mysql` container only creates `root` and the database, so following the documented flow literally would leave `DATABASE_USERNAME`/`DATABASE_MIGRATION_USERNAME` non-existent and every connection would fail.

RED (manual, infra-level, not unit-testable): started a plain `mysql:8.4.5` container from the same pinned digest with no `initdb.d` mount at all (`docker run --rm -d -e MYSQL_ROOT_PASSWORD=... -e MYSQL_DATABASE=quan_ly_sach ...`); once healthy, `SELECT user, host FROM mysql.user WHERE user IN ('app','migration')` returned zero rows.

Fix: new `BE/docker/mysql/init-prod/01-create-app-users.sh`, mounted read-only at `/docker-entrypoint-initdb.d` in `compose.prod.yml`'s `mysql` service. Reads `DATABASE_USERNAME`/`DATABASE_PASSWORD`/`DATABASE_MIGRATION_USERNAME`/`DATABASE_MIGRATION_PASSWORD`/`MYSQL_DATABASE` from the same `env_file` mysql already loads, and grants `SELECT, INSERT, UPDATE, DELETE` to the app user and `ALL PRIVILEGES` to the migration user, both scoped to that one database. Runs once, only on first init of an empty data directory (same MySQL behavior already documented in this session for `MYSQL_ROOT_PASSWORD`).

First re-run still failed (`bad interpreter: Permission denied`): the script was not executable, and the official mysql entrypoint runs `.sh` files as a subprocess, not by sourcing them, so it needs the `+x` bit — the file-writing tool used to create it does not set permissions. Fixed with `chmod +x`; this is itself a real finding worth naming, since it is exactly the kind of bug that only surfaces by actually running the container rather than reading the script.

GREEN: `docker exec docker-mysql-1 mysql -uroot ... -e "SELECT user, host FROM mysql.user WHERE user IN ('app','migration')"` returns both; `SHOW GRANTS` confirms least privilege for each; `mysql -uapp -p*** -e "SELECT 1" quan_ly_sach` succeeds; `docker compose run --rm api node dist/tools/db-cli.js up` (using `DATABASE_MIGRATION_USERNAME=migration`) applied all 10 migrations; `api`/`worker` then ran at runtime as `app`, not `root`.

### 8. `MYSQL_DATABASE: ${DATABASE_NAME:-quan_ly_sach}` in `compose.prod.yml` silently ignored a customized `DATABASE_NAME`

Docker Compose's `${...}` interpolation in the YAML resolves only from the shell/`--env-file`, never from a service's own `env_file:` entries. Customizing `DATABASE_NAME` in `env.production` (the documented customization point) would leave MySQL creating `quan_ly_sach` regardless, while api/worker tried to connect to the new name: total connection failure, invisible until an operator deviated from the shipped default. Confirmed via `docker compose config` before the fix.

Fix: removed the `environment:` override entirely; added `MYSQL_DATABASE=quan_ly_sach` directly to `env.production(.example)`, next to `DATABASE_NAME`, so the mysql container's own entrypoint reads it from the same `env_file` every other service already uses, with a comment tying the two together.

GREEN: `docker compose -f docker/compose.prod.yml config` no longer shows the interpolation; a fresh `mysql` bring-up creates `quan_ly_sach` from `MYSQL_DATABASE` and the app connects successfully using the same `DATABASE_NAME`.

### 9. Missing `trust proxy` meant every real client behind nginx shared one IP-based rate-limit bucket

`nginx.conf` sets `X-Forwarded-For`/`X-Real-IP`, but nothing in the app configured Express to trust them (`grep -rn "trust proxy" src` returned nothing). `req.ip` in `auth.controller.ts` therefore always resolved to the proxy container's internal docker-network address, so `` `login:ip:${clientIp}` ``/`` `forgot:ip:${clientIp}` `` (`auth.service.ts`, `password-recovery.service.ts`) all collapsed onto one bucket: five failed logins from any single real client would lock out every user on the intranet for the configured rate-limit window. This is a direct security consequence of adding the reverse proxy in this task, not a pre-existing issue.

RED: `test/unit/setup-app-trust-proxy.spec.ts` — boots a probe app, sends a request with a spoofed `X-Forwarded-For`, asserts the default behavior ignores it (already true) and that it is honored once `TRUST_PROXY=1` (failed before the fix: `req.ip` stayed `::ffff:127.0.0.1` regardless of the header).

Fix: added `trustProxy: boolean` to `AppConfigService` (default `false`, `TRUST_PROXY=1` to enable), wired into `configureApp()` via `app.getHttpAdapter().getInstance().set('trust proxy', 1)`, guarded so it is off unless explicitly enabled — trusting it unconditionally would let any direct caller spoof `req.ip` and bypass the rate limit entirely, which is worse than the original bug. `env.production.example` now sets `TRUST_PROXY=1` by default with a comment explaining why: `compose.prod.yml`'s own topology already puts exactly one nginx hop in front of `api` (which itself publishes no port), so the assumption holds for this compose file specifically, not as a universal default.

GREEN: same test passes both directions (default ignores the header; `TRUST_PROXY=1` honors exactly the first hop).

### 10. `OutboxWorkerRunner`'s catch-branch backoff had no floor

`JOB_POLL_SECONDS=0` is a valid, documented value (poll immediately when work is found); the RED/GREEN test for finding 4 above even exercises the runner with it. On a *persistent* (not transient) failure, the catch branch's `sleep(this.config.jobPollSeconds * 1000)` degenerates into a tight, unthrottled retry loop.

RED: extended `test/unit/outbox-worker.runner.spec.ts` with a case that fails every iteration under `jobPollSeconds: 0`, spying on `setTimeout` and asserting every catch-branch delay is at least 1000ms; failed before the fix (delay was 0).

Fix: `await sleep(Math.max(1000, this.config.jobPollSeconds * 1000))` in the catch branch only (the success-path sleep is unchanged, so `JOB_POLL_SECONDS=0` still polls immediately when there is no error).

GREEN: same test passes.
