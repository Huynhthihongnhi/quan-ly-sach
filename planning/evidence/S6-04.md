## Report definitions (matches BE/docs/06-business-flows.md #10 exactly)

- Circulation: checkouts by `checked_out_at` in range; returns/lost by `closed_at` + state in range; `currentlyBorrowed`/`currentlyOverdue` computed at request time, reported separately from the period counts (never mixed into the same total).
- Inventory: `titles` = `books` row count, `physicalCopies` = `book_copies` row count (title vs physical copy is explicit in the JSON field names); `available` uses the exact same `NOT EXISTS` invariant as `CirculationInventoryService`; `reservedActive`/`borrowed` come from `loans` and are reported separately from the `repair`/`lost`/`retired` `condition_state` group. Snapshot only (current state); does not accept `from`/`to` because the schema has no historical copy-condition data, matching the documented limitation.
- Purchases: `submitted` by `created_at` in range, `approved`/`rejected` by `reviewed_at` + state in range, `pendingNow` is a current count (not range-bound); aggregate JSON never includes requester identity.

## Date range handling

`from`/`to` are required local `YYYY-MM-DD` dates, both inclusive, converted to a half-open UTC range `[localMidnight(from), localMidnight(to+1))` for Asia/Ho_Chi_Minh (UTC+7, no DST). Capped at 366 days inclusive. Hand-verified boundary case in the integration suite: a loan checked out at `2026-09-13T16:59:00Z` (= 2026-09-13 23:59 local) counts only in the `to=2026-09-13` query, and one at `2026-09-13T17:30:00Z` (= 2026-09-14 00:30 local) counts only in the `from=2026-09-14` query — no double count, no gap.

## CSV export design

- Circulation and inventory CSV are single-row aggregate exports (no per-record detail, no PII).
- Purchases CSV exports per-request detail rows (`id, title, authorText, publicationYear, state, createdAt, reviewedAt, reviewReason`) deliberately excluding `requesterId`/`reviewedBy`, so there is a real escaping surface without exposing requester identity — matches "Báo cáo tổng hợp mặc định không xuất tên/email/mã thẻ".
- `csvField()` (`BE/src/modules/reports/csv.util.ts`) prefixes a leading apostrophe when a text cell starts with `=`, `+`, `-`, `@`, tab, or CR (OWASP CSV-injection trigger set), and wraps/doubles quotes for cells containing a comma, quote, or newline. Applied to every user-controlled text cell; never applied to server-computed numeric cells.
- The purchases CSV query caps at `LIMIT 10000` rows; combined with the 366-day range cap this bounds worst-case export size. It is a plain non-locking `SELECT`, so it does not hold locks. True streaming for arbitrarily large exports is not implemented — documented residual, not required by the 366-day-bounded design.

## Independent review and fixes

A Countervoice-style review (`code-reviewer` subagent, read-only, independently re-derived the timezone math and re-read the SQL/CSV logic rather than trusting the tests) found two real defects in this task, both fixed and covered by regression tests:

1. `ReportRangeError` always reported `field: 'from'` in the 422 response even when `to` was the invalid one (e.g. `to=2026-02-30`). Fixed by tagging the error with the actual failing field at each throw site; added `reports-date-range.util.spec.ts` case "tags the error with the field that actually failed, not always from".
2. The CMS dashboard's default date range used `Date.toISOString()` (UTC calendar date) instead of the library's Asia/Ho_Chi_Minh local date, so for part of every day (UTC 17:00-23:59) the default "to" date was one day behind the actual local "today". Fixed with an `Intl.DateTimeFormat` helper pinned to `Asia/Ho_Chi_Minh`.

Everything else the reviewer checked (permission gates match the contract table, CSV neutralization covers all six OWASP trigger characters and is applied only to user-controlled cells, the inventory "available" query is a verbatim copy of the existing circulation invariant, idempotency/PII/timezone math) was confirmed correct with no changes needed.
