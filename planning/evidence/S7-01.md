## P1 findings, fixed with RED then GREEN

### 1. CONTRACT_TEST_ACTOR bypass had no production boot-time gate

`BE/src/modules/auth/guards/csrf.guard.ts`, `BE/src/modules/auth/guards/mutation-origin.guard.ts`, and `BE/src/modules/auth/middleware/session-context.middleware.ts` all read `process.env.CONTRACT_TEST_ACTOR === '1'` and, combined with a client-supplied `x-contract-test-actor` header, bypass CSRF validation, bypass origin/`X-Requested-With` verification, and fabricate `req.actor` (arbitrary `userId` and `permissionCodes` parsed straight from the header's JSON) with no signature or session backing it. This is a full authentication and authorization bypass by design for contract tests (`test/setup-contract-env.ts` sets the flag). Nothing in `AppConfigService` or anywhere else refused to boot if this flag were ever set in a real deployment: an operator accidentally copying a CI/test `.env` into production would silently grant any caller full impersonation of any user and any permission set.

RED: added a test in `test/unit/app-config.service.spec.ts` constructing `AppConfigService` with `NODE_ENV=production` and `process.env.CONTRACT_TEST_ACTOR=1`, expecting it to throw; ran it first and confirmed it failed (no throw).

Fix, first pass: `BE/src/config/app-config.service.ts` constructor threw `ConfigurationError` when `nodeEnv === 'production' && process.env.CONTRACT_TEST_ACTOR === '1'`.

Fix, after independent countercheck (see "Independent review"): the exact-match denylist against `'production'` left `staging`, an unset `NODE_ENV` (defaults to `'development'` per `readString`'s fallback), or any other spelling fully exploitable. Inverted to an allowlist: the gate now throws whenever `nodeEnv !== 'test' && process.env.CONTRACT_TEST_ACTOR === '1'`. Verified every place that sets `CONTRACT_TEST_ACTOR=1` (`test/setup-contract-env.ts`, `test/setup-integration-env.ts`, `test/integration/http-harness.spec.ts`) also runs under `NODE_ENV=test`, and confirmed the containerized path (`BE/Dockerfile` sets `NODE_ENV=production`) was already covered even before this correction; the gap was specifically an uncontainerized `npm start` on a staging/undefined-env box with a leftover flag.

GREEN: `test/unit/app-config.service.spec.ts` now covers `production`, `staging`, and unset `NODE_ENV` all throwing, and `test` explicitly not throwing; full `npm run validate` and `test:contract` runs confirm contract/integration test runs are unaffected.

### 2. `identity_challenges` created_at bypassed the injectable Clock

Migration `BE/migrations/000005_challenge_outbox.up.sql` has `created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)` and `CONSTRAINT chk_challenges_expiry CHECK (expires_at > created_at)`. The `IdentityChallenge` entity's `createdAt` was a plain `@Column`, never set explicitly by `ChallengeRepository.create`, so every insert silently used MySQL's real wall-clock time for `created_at` while `expiresAt` was computed by application code from the injectable `Clock` (`CLOCK` token), which four spec files pin to a fixed calendar date in the past (`2026-09-13`) for deterministic fixtures. Once real time passed that date, `expiresAt < created_at` and the CHECK constraint threw a 500 on every challenge creation, failing `password-recovery-security.spec.ts`, `challenge-consumption-security.spec.ts`, `outbox-security.spec.ts`, and `s2-account-acceptance.spec.ts` (21+4 tests). This was flagged as a pre-existing, out-of-scope issue in `planning/evidence/S6-05.md`; S7-01's own mandatory `security` test class was red because of it, which brings the fix into this task's scope.

RED: confirmed via `SECURITY_TESTS=1 npx jest --testPathPatterns=password-recovery-security` failing with `QueryFailedError: Check constraint 'chk_challenges_expiry' is violated` before the fix.

Fix: threaded an explicit `createdAt: Date` through `CreateChallengeInput` (`BE/src/modules/challenge/challenge.types.ts`), `ChallengeService.createChallenge`, and `ChallengeRepository.create` into `manager.create(IdentityChallenge, {...})`. `ChallengeOutboxOrchestrator.enqueueChallengeEmail` (the only caller, already injects `Clock`) now passes `createdAt: this.clock.now()`, so `created_at` and `expiresAt` are computed from the same clock and the CHECK constraint can never be violated by clock skew again. Did not touch the FakeClock dates in the affected spec files (that would only postpone the same drift).

GREEN: all four files pass; full `SECURITY_TESTS=1`/`ACCEPTANCE_TESTS=1` runs confirm 0 regressions.

### 3. `mysql2` and `typeorm` had known-exploitable advisories with non-major fixes available

`npm audit --omit=dev` on the BE production dependency tree found, among others: `mysql2 <=3.23.0` ("MySQL2: Auth Plugin Downgrade to mysql_clear_password Leaks Plaintext Credentials", decompression-bomb DoS) and `typeorm <=0.3.30` ("TypeORM vulnerable to SQL injection via crafted request to repository.save or repository.update", "SQL Injection in UpdateQueryBuilder/SoftDeleteQueryBuilder orderBy", migration:generate template-literal injection). Both fixes are patch/minor bumps within the currently pinned major version (`fixAvailable` without `isSemVerMajor`), not the NestJS-11-to-12 major chain (see "Not fixed" below).

Fix: `BE/package.json` `mysql2` 3.14.1 -> 3.24.4, `typeorm` 0.3.25 -> 0.3.31 (the only two direct dependency version strings changed in `package.json`); `npm install` to update the lockfile; then `npm audit fix` (no `--force`) to also pick up the transitive `js-yaml`/`lodash`/`path-to-regexp` bumps pulled in by `@nestjs/swagger`, all non-major. Independent countercheck flagged that `package-lock.json` itself moved further than that: `@nestjs/swagger`'s own caret range re-resolved to 11.4.7 (from 11.2.0) pulling `swagger-ui-dist` 5.21.0 -> 5.32.13 along with it, and some transitive dev packages picked up their own majors (e.g. `js-yaml` 4 -> 5 inside unrelated tool chains). None of this is evidence of tampering (it is npm's normal re-resolution inside already-declared semver ranges, not something this task typed in), but "only mysql2/typeorm changed" is accurate for `package.json`, not for the full lockfile, and is recorded here precisely for that reason.

GREEN: full `npm run validate` plus every DB-backed test class (`security`, `integration`, `acceptance`, `concurrency`) re-run after the bump with zero new failures (same single pre-existing `catalog-schema.spec.ts` failure as before, unrelated).

## Additional findings (not P1, documented and not silently fixed)

- **Low: `ContractDemoModule` is registered unconditionally in `BE/src/app.module.ts`**, so `/api/v1/demo/*` is live in every environment including a real production deployment, not gated to test/contract runs. Read the controller in full: every route returns hardcoded in-memory sample data with no database access, no persistence, and no PII; `demo.read` is a real permission that must be explicitly granted (no default role has it). Impact is low (dead scaffold surface, not an exploitable data or auth issue), but it is unnecessary production attack surface. Not fixed here because `test/contract/http-contract.spec.ts` depends on these exact routes; gating registration behind an environment check or moving the contract fixture elsewhere is an S7-02 (production config) decision, not an S7-01 patch.
- **Observation: `sanitizeAuditDetails` (`BE/src/modules/audit/sanitize-audit-details.ts`) redacts sensitive-looking keys only at read/mapper time** (`BE/src/modules/audit/mappers/audit-event.mapper.ts`), not at write time. Every current caller of `AuditService.append` across `purchases`, `auth`, `access`, `circulation`, `cards`, `catalog`, `users`, and `bootstrap` services was read directly; none pass a password/token/session/csrf/cookie-shaped key today, so nothing sensitive is currently persisted in `audit_events`. This is a defense-in-depth gap (a future caller could still write a raw secret to the table, invisible only through the API, not from a direct DB read) worth closing at write time as a low-cost hardening item, not a live vulnerability today.
- **SQL injection surface reviewed in full, no findings**: every `dataSource.query`/`manager.query` call site (`rate-limit.repository.ts`, `challenge.repository.ts`, `circulation-inventory.service.ts`, `loan-reminder-scheduler.service.ts`, `loan-reservation-expiry.service.ts`, `loans.repository.ts`, `notification-deliveries.repository.ts`, `outbox.repository.ts`, `purchases.repository.ts`, `reports.repository.ts`, `health.controller.ts`) uses `?` placeholders; no template-literal interpolation into any raw SQL string exists anywhere in `src/`. Every dynamic `.orderBy(column, ...)` call (`user.repository.ts`, `access.repository.ts` x2, `catalog-public.repository.ts`) resolves `column` through a closed ternary that always ends in a hardcoded literal, never the raw input value, so an unrecognized sort field cannot reach the query regardless of DTO validation. New regression test: `test/security/sql-injection-security.spec.ts`. Independent countercheck caught that the first version of this test's tautology assertions (`title=' OR '1'='1`, etc. all asserting an empty result) were vacuous against the freshly-reset, empty catalog table: an unparameterized query would have "passed" the same assertion by returning nothing to leak. - **Error-response leakage reviewed, no findings**: `ApiExceptionFilter`'s catch-all branch (`BE/src/common/http/filters/api-exception.filter.ts`) always returns `{code: INTERNAL_ERROR, message: 'An unexpected error occurred.'}` to the client for any unhandled exception, logging the real stack server-side via `Logger.error` only. New regression test: `test/security/error-leak-security.spec.ts`, which plants a fake secret string in a stubbed `AuditService.append` throw and asserts the HTTP response never contains it.

The reverse-proxy half of this question (does the eventual nginx/production config also avoid exposing the storage directory) is explicitly S7-02 scope, not verified here.

## Low-severity fix from the countercheck

`ChallengeOutboxOrchestrator.enqueueChallengeEmail` called `this.clock.now()` three separate times (for `revokedAt`, `createdAt`, and `availableAt`) instead of reusing the single `now` its callers (`password-recovery.service.ts`, `users.service.ts`) already computed to derive `challengeExpiresAt`. With `FakeClock` (static until manually advanced) and realistic TTLs this was harmless in practice, but it meant the fix in finding 2 relied on the two calls happening to return the same value rather than being guaranteed equal by construction; an extremely short TTL could in principle still trip `chk_challenges_expiry` again. Fixed by adding `now: Date` to `EnqueueChallengeEmailInput` and having the orchestrator use the caller-supplied `now` for all three timestamps instead of calling the clock itself; removed the now-unused `CLOCK` injection from the orchestrator's constructor. Updated the three direct calls in `test/security/outbox-security.spec.ts` (which construct the orchestrator without going through the two production callers) to pass `now: fakeClock.now()`. Full `security`/`integration`/`acceptance`/`concurrency` suites re-verified green after this change (see "Independent review" for the run history, including one false-alarm regression from running two DB-truncating suites concurrently against the shared test database, resolved by re-running them sequentially).
